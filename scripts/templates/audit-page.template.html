The pack format disagrees with the invoice

Each item's packChain is compared against its primary supplier offer's stated format. A disagreement does not by itself mean the cost is wrong — it means one of the two is stale, and the data does not say which. The chain is stale when a supplier changed pack size (approve writes the new price over the old format, so the cost is wrong by the ratio); the format triple is stale when someone edited the item afterwards. Check lastUpdated on both, and use the BC band as the tiebreaker. In this snapshot it was an even 16 / 16.

The count unit is shadowed by a pack level

A chain level is named with the same token as the base unit (each), so basePerUnit(item, 'each') resolves to the pack size instead of 1. Valuation is unaffected — stockValue uses pricePerBaseUnit × stockOnHand — which is why this never showed up on a cost report. The count screen shows the wrong number. Fix by renaming the middle level to a container token (case, pack, tray).

STATCAN bands derive from Statistics Canada table 18-10-0245-01, Monthly average retail prices for selected products, GEO = British Columbia. Retail is an upper bound on wholesale, so bands sit near 0.4–1.0× the retail figure. FS bands are BC foodservice distributor ranges — industry judgement, not a published quote. Treat an FS flag as worth a look, not as proof.
